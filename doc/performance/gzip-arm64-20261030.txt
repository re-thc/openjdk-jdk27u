All reads consume the whole payload and EOF. GZIP timing includes allocating
the output buffer, ByteArrayInputStream, GZIPInputStream and owned Inflater,
header parsing, payload reads, trailer validation and close. Default input
buffer is 512 bytes; buffered is 8192. Output chunks are min(size+1, 8192).
Fixture preparation and validation, plus JVM/JIT warmup, are outside timing.
Repeated data repeats a seeded random 256-byte pattern; random data uses
the same fixed seed.
The two content labels produce identical fixtures at 64 bytes and should
not be treated as independent payload populations at that size.

Fresh Inflater creates and closes an Inflater for each complete stream.
Reused Inflater creates one per batch of 16 complete streams and closes it
inside the timed batch; reset, setInput and a fresh output buffer per stream
are timed. Creation and close are therefore amortized over 16 streams, not
omitted in setup/teardown. All scores normalize to one stream.

Each A/B observation uses a fresh JVM, one JMH thread, 256 MiB heap and
SerialGC, with default ZIP/CRC intrinsics. Five A/B rounds reverse case
order between rounds. Correction: the order formula and case reversal kept
the A/B order fixed per case; they did not alternate AB/BA within each case.
All five original unprofiled 64-byte default-buffer pairs ran A then B.
That suite is interleaved but not order-balanced. Main runs warm up 3 x 400 ms and
measure 3 x 400 ms. The statistic below is the median measurement iteration
per fork, then the median of five fork medians. Negative time change is
faster. No correctness tests or other benchmark jobs ran concurrently;
reference tests finished before the first benchmark. Host background tasks,
CPU placement, clock rate and ASLR were not fixed. Initial thermal inspection
reported no recorded thermal/performance warnings.

The main bulk results are stable: 64 KiB to 1 MiB GZIP reads take about
48-61% less time on repeated data. Buffered random reads take about 56-59%
less time; default-buffer random reads take about 13% less time. Small input
chunks require many inflate calls, limiting the benefit of CRC fusion.
Raw fresh/reused Inflater medians are approximately flat to 3.5% faster.
These are local workload observations, not universal throughput guarantees.

The empty default-buffer read has a small reproducible cost, about 4 ns
(roughly 1.6%). The native setup/completion contract adds some work even
without payload CRC work to save. This does not justify another size-based
policy or separate initialization path. The 1-KiB reads improve by about
8-11% with this fixture.

The 64-byte investigation is deliberately retained, including adverse
results. Short main runs show separate fast/slow fork populations on both
builds, around 205 and 250 ns with the default buffer. The random-labelled
five-fork median is 20.6% worse for B, while the identical repeated-labelled
fixture is 2.1% better. Buffered short medians likewise have opposite signs.
This is substantial variability; the short medians alone cannot establish
either a reliable tiny-read gain or an implementation regression.

Native dispatch was verified with LLDB on the running candidate JVM:
ZipRuntime::process_c1 -> ZipRuntime::process -> ZIP_Process -> zng_inflate
-> updatewindow -> raw_crc_update_c. The live dispatch table resolves CRC
and CRC-copy to crc32_armv8_pmull_eor3 and crc32_copy_armv8_pmull_eor3.
The exact-class GZIP activation test reports supported=true. C2 compiler
logs independently confirm the inflate intrinsic is emitted. This is ARM
hardware CRC/PMULL/EOR3 dispatch, not the x86 persistent-folding backend.
The scalar wrapper name raw_crc_update_c does not indicate scalar CRC:
that wrapper dispatches to the selected ARM implementation.

Remaining uncertainty: sub-microsecond fork populations; cold JVM startup
and first-ever class/native resolution; other Apple Silicon generations;
concurrent readers, direct-buffer performance, real files/networks and other
payloads/fragmentation patterns. The correctness tests exercise more shapes
than the timing matrix. This is one host with warm JIT and allocator caches,
mostly SerialGC, plus the small G1 control. No x86 performance claim is made.
